## Findings and rationale

Re-read existing session output (includes csrfToken), Java security/current-account filter, server-owned BFF header forwarding, fixed mapping targets, receipt checks and reconciliation GET. New gateway must sanitize session info and retain Java authorization; existing proxy alone does not supply a safe agent loop. There is no reason to invent reconciliation-by-ID or call the mutating POST.

The chosen design signs AI requests using a BFF-only Ed25519 private key and a Python public key. Context binds route, raw body and declared metadata; BFF keeps current-request identity and pending calls. Signed transport is never proof of a current Java session by itself. Controller is stateless in Python across steps: BFF supplies bounded sanitized prior results, current authorization and a new nonce per step. No detached privileged continuation exists in the design. Key provisioning/interoperability and all enforcement remain future work.

Schema validation explicitly accepts some shapes that still require runtime denial (expired context, final-step tool, duplicate source-header projection and invalid Java restart eligibility). Those examples make the limit visible: schema success cannot stand in for cryptography, time, scope, semantic correctness or DB nonmutation proof.

## Security/backward compatibility/failure-mode review

Thirty-second outer lifetime, four model steps/three tools, nonce uniqueness, exact pending-call sequence, endpoint-specific capability/scope, metadata/raw-byte digest and result projections are specified. Unknown encoding/headers, unsupported/scanned documents, missing policy, stale approval, denied session/scope, provider budget exhaustion and lost business acknowledgement have explicit failure behavior. JSON schema cannot enforce these runtime invariants alone. The public key does not grant a Java privilege, a static shared secret does not replace user authorization, and the actor reference is not vendor tenancy.

Residual: real BFF/Python key interoperability, replay concurrency, role revocation, parser limits, active document ACLs, provider cost reservation, retention and deployment networking remain unimplemented. R08 advisories from P00 remain OPEN. Single-host private-network HTTP is explicitly local-only and lacks confidentiality. No critical invariant may be declared verified until the required negative/runtime/DB assertions execute.

## Interview deep-dive

1. **Why are both signed context and current Java authorization needed?** The signature binds Python input to BFF-derived scope; only Java can revalidate the live OPERATOR account and authorize business GETs. Transport integrity is not a durable user grant. Evidence: ADR 0002, gateway protocol and source recheck.
2. **What do 76 passing checks actually prove?** The OpenAPI/schema structures, examples, closed registry and declared contract policies match expectations. They do not execute crypto/ACL/time/session/parser handlers or business writes. Four intentionally valid-but-runtime-unsafe example shapes demonstrate that limit.
3. **How do you prevent AI from applying stale supplier quantities?** Keep mapping as a draft, preserve exact bytes and existing three-field contract, hand off to Java's human receipt/active-profile/version/dedupe workflow, and never treat 202 or timeout as completion. Evidence: I04–I07 and existing SupplierOnboardingService; implementation regression proof belongs to P10.
