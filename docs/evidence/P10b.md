## Delivered boundaries

- Opt-in integrated mapping verifies Ed25519 context/body/operation/scope/step,
  replay nonce and deadline, then validates one BFF-owned active matching profile
  snapshot. It uses the existing mapper and immutable AI-only draft storage.
  Integrated mode exposes no unsigned QA/citation/demo bypass. Fake/local only;
  no paid provider path. [Transport decision](../adr/0006-signed-mapping-snapshots.md).
- BFF accepts original base64, declared encoding and source profile ID/version;
  rejects browser-supplied vendor/actor/candidates/mapping authority. It checks
  current OPERATOR/CSRF, reads Java profiles, derives vendor/synthetic document
  scope, signs exact JSON, checks returned raw SHA256/profile binding and rechecks
  session/profile. Only fixed Java GETs exist in the draft handler. Cookie/CSRF/
  Java trust secrets/private signing key never enter the Python runtime request.
- Feature-OFF minimal Operations Ledger panel shows draft reason/uncertainty,
  bounded authorized SOP excerpts when linked, current/edited header differences,
  explicit vendor/encoding and original checksum. Rules are default; local AI is
  optional. Manual editing remains available if draft inference fails.
- Operator separately reviews/edits, creates an immutable **inactive** profile,
  activates it, and adopts the same frozen original bytes for the unchanged
  preview/explicit confirm workflow. No auto preview/confirm/import or new agent
  write tool exists. Unknown create/activate outcomes require profile inspection;
  unknown confirm outcomes use [P10a recovery](P10a.md). UI locks are browser-local;
  Java remains authoritative across reloads/tabs/concurrency.

Java source/tests/contracts and npm lock are unchanged. Human profile calls keep
existing JSON contracts; preview/confirm keep exact text/csv/raw-byte/receipt
contracts. The AI-only planned transport changes to a signed JSON wrapper,
documented in OpenAPI/shared schema: original max5MB, wrapper max6.7MB. A current
profile snapshot does not certify row validity, future vendor activation or
production tenancy.

## Real browser, Java, BFF, Python and database

[Final real smoke](P10b-real-smoke-final.json) starts owned disposable Java PG/Redis
and real Java/BFF/Python on loopback. Keys/account credentials are ephemeral.
The harness gives Python the public verification key and its dedicated AI DB credential;
the report checks its environment lacks Java/BFF/private signing secrets. AI is
fake/rule for reproducible plumbing, not a real LLM quality trial.

Ten checks include signed draft as a business read, tampered original409,
stale/missing CSRF403, guest confirm401, a correctly signed controlled-expired
receipt409, deactivated profile409, stock/product changes409 and a wrong mapping
with zero acceptable rows400. Each compares exact counts and sorted JSON-content
hashes of eleven business tables. Manual fault injection precedes each rejection
snapshot and targets the runner's disposable database only.

The real headless browser signs in as the current synthetic OPERATOR and performs
both supplier A CP932 and supplier B UTF-8 journeys. It gets a signed draft,
explicitly creates an inactive profile, separately activates, previews the same
file, reviews and confirms. For B the test intercepts a **real Java202 after the
job exists**, intentionally returns502 to the UI, checks the lock, inspects the
real job, prepares/reviews again and explicitly retries. Java returns the same
job ID. There are exactly two jobs/two browser-created profiles for the two
journeys. With the worker off, inventory stock/movements remain unchanged and the
UI says pending. After an owned Java restart enables its worker, both jobs reach
COMPLETED with one applied row. Fresh preview + repeated confirmation after
completion returns each original ID/status and leaves all eleven tables unchanged;
observed stock is VM-001=32 and VM-002=60. No double application is inferred merely
from an HTTP202.

The controlled wrong AI hint is a browser mock followed by automated human-style
correction; the real wrong-profile case is an explicit test fixture. Neither
establishes real model accuracy or independent human acceptance.

The first [real run](P10b-real-smoke-v1.json) failed in the browser helper: it ticked
the mapping approval before renewed preview finished rendering. The first wait

The wait was then applied at renewed preview; [v3](P10b-real-smoke-v3.json) passed.
The final run adds missing-CSRF/guest negatives and completed replay snapshots.
Failures/logs are retained; they are not counted as passes. All owned service
