## Actual results and selection

There are 8 train, 8 dev and 12 test questions. All three methods execute for each, yielding 84 saved predictions. The test split contains eight positive questions and four zero-relevance cases. Positive metrics exclude the four zero-relevance cases rather than calling them correct answers. All positive grades are 2; nDCG does not imply independent multi-level relevance annotation.

These are **retrieval-only, provisional-label figures**, not 100% answer accuracy or production reliability. Train dense Hit@1 was only 0.5; train hybrid Recall@5 was 0.625 versus dense 1.0. Those failures remain visible. [Full train/dev/test tables, query-language breakdown and failure analysis](../../evals/retrieval/README.md) prevent the tiny test's perfect dense figure from hiding weaker examples.

Dev MRR@3/Recall@5 tied between dense and hybrid at 0.9375/1.0. The preregistered next tie-break was measured median latency: 41.18 versus 45.95 ms. Dense was selected **before** test inference as the local candidate for P07. Single-pass small-sample timing is noisy; no stable production latency advantage is inferred. The exact selected config remains [frozen](../../evals/retrieval/selection.json).

No forbidden document is returned in 84 predictions. Two access-denied test questions return zero in every method without embedding. The two unknown-answer questions still receive candidates: retrieval does not decide answerability/abstention, which remains P07 work. No live signed-context/BFF authentication boundary is introduced here.

Measured query usage: **52 local embedding calls, 928 valid input tokens, $0 provider inference billing**. Local CPU energy/hosting cost is NOT MEASURED. ONNX runs on CPU from an existing pinned bundle; there is no inference API request or new model download. P05 corpus-embedding work is not charged again as P06 query cost. Reranking is absent, not simulated by selecting examples.
