# Scoped PostgreSQL retrieval

P06 implements internal Python retrieval and an offline evaluation CLI. The HTTP service still exposes health/readiness/runtime OpenAPI only. Signed BFF identity remains P09, grounded question answering P07, and CSV draft mapping P08. The selected dense baseline is a measured local recommendation, not a production deployment.

## Implemented methods

`Retriever.search(Actor, SearchRequest, method)` accepts `lexical`, `dense` or `hybrid`:

- Lexical executes actual PostgreSQL `to_tsvector`, `websearch_to_tsquery` and `ts_rank_cd`. Quoted regex-extracted query words are combined with configurable OR/AND semantics; all values are bound parameters. Text configuration is a strict `english`/`simple` enum. Migration 0003 installs real GIN expression indexes for both configurations. [PostgreSQL's documentation](https://www.postgresql.org/docs/17/textsearch-controls.html) describes parsing and ranking. This baseline materializes authorized candidates before ranking; the planner may scan that materialization rather than use the base-table GIN indexes. No index-use/performance benefit is claimed.
- Dense executes actual pgvector cosine distance `<=>` on the fixed registered vector column. It uses **exact search**, with deterministic chunk-ID tie breaks, no ANN index or candidate approximation. The [pgvector project](https://github.com/pgvector/pgvector#exact-search) documents exact search and distance operators. Real mode uses the pinned P05 multilingual E5 local query prefix/model; fake 32-dimensional mode is explicitly marked non-semantic and used only for plumbing CI.
- Hybrid uses weighted reciprocal rank fusion `sum(weight/(constant+one_based_rank))` over lexical/dense candidate lists from the same transaction. Defaults are equal weights and constant 60, following the [RRF paper](https://plg.uwaterloo.ca/~gvcormac/cormacksigir09-rrf.pdf). It does not add raw lexical and cosine scores, and is **not a reranker**. No second-stage reranking model is implemented; `reranker="none"` is the only accepted value.

[`RetrievalConfig`](../src/vmarket_ai/retrieval/spec.py) controls top_k (1–5), pool (5–100), chunk size/overlap through the required compatible ingestion fingerprint, lexical config/match mode, query normalization (`nfc` or `verbatim`), and RRF weights/constant. Changing chunk settings does not reinterpret existing rows: re-ingest/re-index with P05 before searching that fingerprint. `SearchRequest` can narrow language/vendor metadata and collection IDs. Cross-language searches need not restrict document language to the question's language. SQLite is rejected with `postgres_required`; no SQLite test is presented as semantic/FTS execution.

## Corpus and authorization boundary

Every method uses the same `authorized AS MATERIALIZED` CTE before score calculation, ordering or LIMIT. It joins the current document snapshot, registered compatible pipeline/model/dimension/vector column, curated/eligible state, effective dates, optional language/vendor filters, requested collection IDs and **the actor's current collection grants**. A user filter only intersects readable collections. No unauthorized source text is materialized in Python and then filtered after ranking.

One PostgreSQL repeatable-read transaction fixes the authorized corpus for lexical and dense branches of a hybrid request. A metadata-only ID/hash query computes a reproducible corpus signature; more than 10,000 eligible chunks fails rather than silently truncating the corpus. Branch pool and final top_k limits are applied after authorization. The benchmark asserts identical signatures for all three methods per query. A later grant revocation does not retroactively cancel an already-open repeatable-read transaction; later requests/source-open checks use fresh grants. Signed context construction and expiry checks are still P09 work. App SQL credentials remain trusted service credentials, not per-user database roles or RLS enforcement.

Results carry source document/version/snapshot/chunk IDs, original hash, location and normalized offsets, component ranks for fused hits, measured total/embedding/ranking latency, token usage and billed embedding cost. The model never sees evaluation labels, partitions, query family, source-version crosswalk or expected answer. It receives only the normalized user question for query embedding. Ranking SQL does not receive gold IDs or relevance grades.

Retrieval audit events store actor UUID, event name, result count and timestamp; they contain no question, source text, provider key, SQL parameter values or caught exception string. Raw per-query text/citations are retained only by the explicitly invoked synthetic evaluation CLI. Provider/model/storage failures use safe codes; invalid vector dimension/model/mode/finite values/norm fails before scoring. An empty authorized corpus returns no hits without invoking the embedding provider. No paid embedding fallback or external inference request exists in this provider.

## Using the internal service

After real P05 corpus ingestion and migration, a trusted local caller can load [the frozen config](../evals/retrieval/config.json), construct `LocalE5EmbeddingProvider` from the pinned bundle, create `Retriever(engine, config, provider)` and await `search` with an authorized internal `Actor`. Local eval actors are provisioned with curator credentials from the fixture's readable-scope context, never from its requested scope or gold labels. This tooling is not exposed as an arbitrary actor/collection-grant HTTP endpoint.

[`evals/retrieval/README.md`](../evals/retrieval/README.md) contains original commands, exact raw runs, selected baseline, Japanese tokenization limits, metrics, cost boundaries, failures and holdout consumption. [P06 evidence](evidence/P06.md) records local checks separately from remote CI. Small provisional-label results do not imply model quality, secure deployed authentication, answer grounding or readiness for production.
